# Decision log: EMI 26.1 port (autopilot, 2026-09-22)

Each entry: decision, why, alternatives rejected, what a reviewer should double-check.

## D1. Build on the MIT community port `link-fgfgui/emi@26.1` via a real `git merge`
- **Decision:** branch `26.1` = upstream `1.21` HEAD (81f6453c) + merge of `link-fgfgui/emi` branch `26.1` (63e8aef1, 95 commits, MIT, same copyright notice), then re-port the upstream commits the fork lacks.
- **Why:** 323 xplat source files, the Yarn to Mojang mapping switch, and about ten breaking Minecraft versions (1.21.2 recipe/client rework, 1.21.4 item models, 1.21.5 components, 1.21.6 GUI render-state rewrite, 1.21.9/11, 26.1 unobfuscation) make a from-scratch port far riskier than building on a port that already compiles, ships on CurseForge, and has months of user bug fixes. The fork's merge-base with upstream is 35392222 and it already cherry-picked upstream up to 1.1.24, so only 8 small upstream commits remain to re-port. The fork was built locally (JDK 25, 2m13s, both loaders) before being adopted.
- **Rejected:** (a) from-scratch port with agents: highest bug risk, weeks of equivalent effort; (b) `Dabolus/MEMI` as base: targets 26.1.1 only, 2 commits, less tested, though its Fabric-Loom + ModDevGradle build layout was noted; (c) squashing the fork into one commit: loses per-commit authorship, while a merge keeps attribution intact and lets upstream `1.21` be merged forward later.
- **Double-check:** licensing/attribution is satisfied by git history plus the unchanged LICENSE; if the maintainer prefers a squash, `git merge --squash` is trivial later.

## D2. Keep `dev.architectury.loom-no-remap` (the fork's build) instead of Fabric Loom + ModDevGradle
- **Why:** it is proven on this exact codebase (fork CI + local build) and keeps the xplat/fabric/neoforge layout and the `transformProduction*` configurations untouched. MEMI's Fabric-Loom + MDG layout is the "official" toolchain, but switching is a build-system rewrite unrelated to the port's correctness.
- **Double-check:** `loom-no-remap` is a SNAPSHOT plugin line; pin to a release (`1.17.x`) if reproducibility matters.

## D3. Upstream's `ProxyRecipeManager` abstraction wins over the fork's `EmiPort.getRecipeMap()` helpers
- **Why:** upstream's last commit ("Introduce some abstractions") was written precisely to isolate recipe-manager access for this port. Keeping upstream's API keeps future merges from `1.21` clean. The implementation delegates to the fork's `EmiAgnos.getRecipeMap()` (Fabric: `ClientRecipeSynchronizedEvent`; NeoForge: `RecipesReceivedEvent`).
- **Double-check:** `ProxyRecipeManager.isAvailable()` on 26.1 means "a RecipeMap has been received from the server", not "world != null".

## D4. Restore upstream versioning (`-SNAPSHOT` unless `RELEASE`); do not bump `mod_version`
- **Why:** the fork embeds the git short hash in the version for its own CI releases. Upstream's convention is simpler and expected by the release workflow. Version/release numbering is the maintainer's call.

## D5. Drop the fork's dev-only `localRuntime` mod lists and its CurseForge auto-publish workflow
- **Why:** about 30 cursemaven/modrinth test mods slow every build and belong to the fork author's workflow; the workflow publishes to *their* CurseForge project (id 1544558). Upstream's `build.yml`/`release.yml` are kept and only updated to JDK 25.

## D6. Dependency versions bumped to the latest 26.1.2-compatible releases available on 2026-09-22
- **Why:** users run the newest loader/API builds; compiling against the latest catches API drift now instead of at runtime. Exact versions are recorded in `gradle.properties`; any bump that failed to compile is noted in the morning report.

## D-PR. Push/PR target
- **Decision:** never push to or open a PR against `emilyploszaj/emi` (origin). That is the upstream maintainer's public repo and the port issue there was closed by the maintainer. Push only to a remote the user owns, if one is configured and authenticated; otherwise leave the branch local and say so.

## D8. NeoForge dev run: register the generated `GlobalMixin` output dir as a loom mod file
- **Decision:** `fabric/build.gradle` and `neoforge/build.gradle` add `modFiles.from(layout.buildDirectory.dir("generated-class"))` to `loom.mods.main` (and the NeoForge block now also lists its own `sourceSets.main`, as the Fabric block already did).
- **Why:** upstream's `generateClassLists` task emits `dev/emi/emi/mixin/GlobalMixin.class` into an extra source-set output dir. `loom-no-remap` 1.17 only hands classes/resources dirs to FML's `InDevFolderLocator`, so on NeoForge the class was outside the mod module and `runClient` died at bootstrap with `NoClassDefFoundError: dev/emi/emi/mixin/GlobalMixin` (the packaged jar was unaffected because `jar` copies the dir). Verified: after the change the NeoForge client joins a world and EMI reloads (3727 recipes).
- **Rejected:** writing the generated class into `build/classes/java/main` (fights `compileJava`'s stale-class cleanup) or into resources (fights `processResources`).

## D9. Resource-level fixes from the runtime review (verified against 26.1.2 / NeoForge 26.1.2.109 bytecode)
- `neoforge/.../accesstransformer.cfg`: removed three `PotionBrewing` field entries that used 1.20.4 names (`POTION_MIXES`, ...) and silently matched nothing (EMI reaches those fields through `BrewingRecipeRegistryAccessor`), and the `Screen#addWidget` entry; `emi.accesswidener` likewise drops `Screen#addRenderableWidget`. All remaining call sites are `this.` calls inside `Screen` subclasses, so `protected` access suffices; AW and AT now widen the same members.
- `neoforge/src/main/resources/pack.mcmeta` deleted: it still declared `pack_format 8` (1.18) and NeoForge computes the mod's pack as incompatible; with the file absent NeoForge synthesises a compatible section (the Fabric jar ships none).
- `assets/emi/recipe/defaults/emi.json`: `minecraft:chain` no longer exists in 26.1 (split into `iron_chain`/`copper_chain`); both new ids listed.
- `assets/emi/tag/exclusions/emi.json`: `minecraft:occludes_vibration_signals` is a block tag only; removed from the item list.
- `assets/emi/lang/de_de.json`: duplicate `key.emi.default_stack` key (second one was the tooltip text) renamed to `config.emi.tooltip.binds.default_stack`.
- `mixin/accessor/SmithingTrimRecipeAccessor` (empty `@Mixin` interface, no members, no references) deleted with its `emi.mixins.json` entry.
- **Left as is (pre-existing upstream behaviour, noted for the maintainer):** `EmiPersistentData` writes `emi.json` to the process working directory; `EmiPacketHandler` passes `"emi"` where NeoForge expects a protocol version (works, cosmetic); the `conversion.*` mixins are Fabric-only so `EmiStackConvertible#emi()` is unavailable on NeoForge (parity hole that predates the port); `StackBatcher`'s Sodium hook still names the pre-rename `me.jellysquid` package (batcher is inactive on 26.1, see D7).

## D10. JEMI: info recipes register synchronously again; the font work is deferred in `EmiInfoRecipe`
- **Decision:** `JemiPlugin.addInfoRecipes` registers on the reload thread (as upstream) and constructs `EmiInfoRecipe` directly. `EmiInfoRecipe` keeps the raw `List<Component>` and wraps it with the font lazily from `getDisplayHeight()`/`addWidgets()` (render-thread callers only). The interim `JemiInfoRecipe` delegate was removed once that root fix landed (25295fa8).
- **Why:** the fork's `Minecraft.getInstance().execute(() -> registry.addRecipe(...))` (commit `fd7eaa89`) ran after the reload had already baked, so JEI "information" recipes were dropped or mutated the recipe lists concurrently. The hazard it dodged is real: on 26.1 `Font.split`/`width` bake glyphs (`GlyphSource.getGlyph` → `FontSet$DelayedBake` → `GlyphStitcher.stitch` → GPU texture creation and unsynchronised mutation of `FontSet.glyphCache`) and must not run off the render thread. No other reload-thread font use was found (`TextWidget` is only built inside `addWidgets`).

## D11. JEMI: the fork's AE2 Inscriber catalyst hack is deleted, not generalised
- **Decision:** `JemiCatalystDetector` (reflection on `appeng.recipes.handlers.InscriberRecipe`) and its use in `JemiRecipe` are gone; slot roles come from JEI again.
- **Why:** one hardcoded mod class and two hardcoded slot names in a generic adapter. AE2 marks those slots `RecipeIngredientRole.INPUT`; if that is wrong it is an AE2/JEI-side issue.
- **Double-check:** with AE2 installed, Inscriber "inscribe" recipes now list the press as an input rather than a catalyst again.

## D12. JEMI: behaviour that upstream had and JEI 29.40 no longer offers is left dropped, not re-invented
- `IRecipeCategory.handleInput` is gone, so `JemiRecipe.JemiWidget.mouseClicked/keyPressed` cannot forward clicks. JEI replaced it with `IRecipeExtrasBuilder.addInputHandler`/`addGuiEventListener`; `JemiRecipeExtrasBuilder` collects both but nothing dispatches to them (upstream never did either). Wiring them needs an `IJeiUserInput`/`InputWithModifiers` implementation — a feature, not a port fix.
- `IRecipeCategory.getBackground()` is gone, so the background draw upstream did before `category.draw` has no equivalent.
- `IRecipeSlotTooltipCallback` is gone (only the rich variant remains), so `JemiSlotWidget`'s legacy tooltip branch cannot exist.
- `EmiDrawContext.enableBlend()`/`resetColor()` are no-ops or per-wrapper on 26.1, and the 2-D `Matrix3x2fStack` has no Z, so upstream's blend/colour/z-offset calls carry no behaviour.
- `IIngredientManager.getTypedIngredientByUid` is gone; `JemiStackSerializer` scans the type's ingredients instead (same result, O(n) per lookup).

## D7. `useBatchedRenderer` is inert on 26.1; EMI's `StackBatcher` is not ported
- **Decision:** `ItemEmiStack.isUnbatchable()` returns `true` unconditionally, `renderForBatch`/`setUnbatchable` are documented no-ops, `StackBatcher.isEnabled()` returns `false`, and the `ui.use-batched-renderer` config comment says it has no effect on 26.1+. The option itself is kept so existing config files stay valid. `StackBatcher` is left in the tree (it is public-ish API: `StackBatcher.Batchable`, `EXTRA_RENDER_LAYERS`) but is now dead.
- **What vanilla does now (verified against the decompiled 26.1.2 client jar, `minecraft-merged-deobf-26.1.2.jar`):** `net.minecraft.client.gui.render.GuiRenderer` holds a `GuiItemAtlas` field and has `prepareItemElements()`, `prepareItemAtlas(Set<Object>, int)`, `invalidateItemAtlas()`, `getGuiScaleInvalidatingItemAtlasIfChanged()` and `submitBlitFromItemAtlas(GuiItemRenderState, GuiItemAtlas.SlotView)`. `GuiItemAtlas` owns a GPU texture plus a `DynamicAtlasAllocator<Object>` keyed on `TrackingItemStackRenderState.getModelIdentity()`, with `tryPrepareFor(Set)`, `getOrUpdate(...)`, `drawToSlot(...)` and `endFrame()`. `GuiRenderState.addItem` records each item's model identity in `itemModelIdentities`. In other words **vanilla already renders each distinct GUI item model once into an atlas and then blits sprites from it**, with slots reused across frames and invalidated on GUI-scale change — the same trick EMI's batcher existed to perform. Oversized items fall back to `OversizedItemRenderer` (picture-in-picture).
- **Perf verdict:** superseded, not a regression. EMI now submits one `GuiItemRenderState` per stack and vanilla deduplicates them; the previous stub was worse than doing nothing, because `StackBatcher.render` called `renderForBatch` (which drew nothing) and then re-rendered the stack *without* `RENDER_ICON`, so a stack's icon was missing for the first frame after each repopulate if a user ever turned the option on.
- **Rejected:** porting `StackBatcher` to 26.1. It replayed an item's `BakedQuad`s into a shared `MeshData`; `ItemStackRenderState` no longer exposes a stable quad list per layer for arbitrary items (the port already had to reach through `ItemStackRenderStateAccessor` just to peek at layer 0 for Sodium sprite ticking), and the result would duplicate `GuiItemAtlas`.
- **Double-check:** in game, that large sidebars/recipe screens are not noticeably slower than 1.21.1, and that the F3 GUI element counts stay sane. If a perf problem does show up, the lever is vanilla's atlas size (`GuiItemAtlas.MINIMUM/MAXIMUM_TEXTURE_SIZE`), not EMI batching.

## D-R1. Custom tag icons restored by resolving model json to flat textures, not by baking models
- **Decision:** `EmiTags.registerTagModels` still discovers `models/tag/**.json` in every namespace and fills `MODELED_TAGS` (so `EmiTagKey.hasCustomModel()` and the `betterTag` tie-break behave as upstream), and additionally resolves each model down to a list of `EmiTags.TagIconLayer` (texture + horizontal slice). `TagEmiIngredient.render` blits those layers over the slot; if a model cannot be resolved it falls back to rendering the tag's first stack, exactly as an unmodelled tag does. Discovery now runs from `EmiTags.reload()` (EMI's own reload) using `Minecraft.getInstance().getResourceManager()`, not from a loader model-registration event.
- **Why:** 1.21 passed the model ids to the loader (`ModelLoadingPlugin` on Fabric, `ModelEvent.RegisterAdditional` on NeoForge) and rendered the resulting `BakedModel` through `ItemRenderer.renderBakedItemModel`. 26.1 has no standalone-model registry or public baked-model rendering entry point of that shape, and the port had simply deleted the whole feature, so every tag rendered as its first item and `hasCustomModel()` was always false.
- **How the resolution works:** walk the `parent` chain through the resource manager, merging `textures` maps (child wins). EMI's own `emi:item/half_item` / `third_item` / `quarter_item` parents are recognised by id and turned into 2/3/4 vertical strips whose bounds match the model elements ([0,8,16], [0,6,10,16], [0,4,8,12,16]) — a model element's south face defaults to the uv of its own x range, so each strip shows that same slice of its texture, which is what the baked model drew. Otherwise the first usable texture key (`layer0`, then `all`, `south`, `side`, `texture`, `end`, `top`, `cross`, `front`, `particle`) is drawn full-slot, with `#key` references followed. A parent whose json does not exist ends the chain rather than failing it — `item/generated` and `item/handheld` inherit from `builtin/generated`, which has no file.
- **Verified:** all 44 shipped tag models under `xplat/src/main/resources/assets/{c,fabric,minecraft}/models/tag/` resolve, and every resulting texture exists in the 26.1.2 client jar or EMI's own assets. This was checked by a standalone re-implementation of the resolver run against the real asset trees. No assets were deleted.
- **Known differences from 1.21:** resource packs that override a tag model with geometry EMI does not understand degrade to the first-stack fallback rather than erroring. (The flat-face and animated-texture caveats originally recorded here were fixed afterwards; see D-R6.2 and D-R6.3.)
- **Rejected:** adding a `getTagModelAgnos` to `EmiAgnos`. Resolution is pure `ResourceManager` + `blit` and needs nothing loader-specific, and adding an abstract method would also break the (currently disabled) `forge` source set. The upstream `EmiAgnos.getBakedTagModel` platform hook therefore stays deleted.
- **Double-check:** in game, that `#c:ingots`, `#c:dyes`, `#minecraft:beacon_payment_items` and `#c:tools/axes` show their split/custom icons, and that the reload-thread resource read causes no hitch (it reads ~45 small jsons per EMI reload).

## D-R2. The tint is global again (static), matching 1.21's `RenderSystem.setShaderColor`
- **Decision:** `EmiDrawContext`'s `color` is a single static field. `setColor`/`resetColor` write it and every wrapper reads it, so a tint set by an outer wrapper is still in effect when deeper code calls `EmiDrawContext.wrap(raw)` on the same raw graphics. `wrap()` also notices when the raw `GuiGraphicsExtractor` instance changes (vanilla allocates a new one per frame in `GameRenderer`, and EMI's recipe screenshot path builds its own) and resets the tint at that point, and `BoMScreen` resets defensively on entry.
- **Why:** the port had made `color` per-instance, so `BoMScreen`'s category-icon tints, `SlotWidget`'s background reset and the `jeb_` search-bar colour were all dropped the moment the call passed `context.raw()` to something that re-wrapped it. A static mirrors what the old global shader uniform did, and GUI rendering is single-threaded.
- **Limitations that cannot be restored on 26.1:** (a) **items cannot be tinted** — they go through `ItemStackRenderState`/`GuiItemRenderState`, which carries no colour multiplier, so a tinted slot tints its background and markers but not the item itself; (b) **vanilla-drawn widgets cannot be tinted** — the `jeb_` easter egg tinted `EditBox.renderWidget`'s own output through the global uniform, and `EmiSearchWidget`'s `super.extractWidgetRenderState` call now renders untinted. EMI's own draws around it (the highlight border, and everything in `BoMScreen`) do tint.
- **Double-check:** in game, that no screen renders tinted after a tinted element (config jump buttons, `MicroTextRenderer`, BoM node lines) — every EMI caller that sets a tint also resets it, but a global is by nature leak-prone.

## D-R3. Fluid sprites already use the loader APIs; the 1.21 calls no longer exist
- **Decision:** keep reading `ModelManager.getFluidStateModelSet().get(fluid.defaultFluidState())` on both loaders; add a null-sprite guard and comments. The audit's suggestion to "restore `FluidVariantRendering.getSprite/getSprites`" and "`IClientFluidTypeExtensions.getStillTexture/getTintColor`" cannot be followed because **neither API still has those methods.**
- **Verified against the jars in the Gradle cache:** in `fabric-rendering-fluids-v1` 6.0.1 (part of Fabric API 0.155.3+26.1.2) the whole `FluidVariantRendering` sprite surface is gone; the module is now `FluidRenderHandler` / `FluidRenderingRegistry` / `FluidRendering`, and `FluidRenderingRegistry.register(Fluid, FluidModel.Unbaked, ...)` feeds vanilla's `FluidStateModelSet` through the module's own `FluidStateModelSetMixin`. `FluidVariantRendering` (in `fabric-transfer-api-v1` 8.0.6) retains only `getTooltip`, `getColor` and handler accessors, and `FluidVariantRenderHandler` only `appendTooltip`/`getColor` — EMI already uses `FluidVariantRendering.getColor` for the tint. In NeoForge 26.1.2.109, `IClientFluidTypeExtensions` only declares `getRenderOverlayTexture`, `renderOverlay`, `modifyFogColor` and `modifyFogRender`; fluid appearance moved to `FluidModel` with `net.neoforged.neoforge.client.fluid.FluidTintSource`, which is exactly what the NeoForge path already reads.
- **Conclusion:** reading the vanilla fluid model set *is* the loader-supported path on 26.1 and picks up modded fluids on both loaders. Audit finding #15 does not apply to this Minecraft version.
- **Double-check:** in game with a mod that registers a custom fluid (e.g. Create or Mekanism) on each loader, that its fluid draws with the right sprite and tint.

## D-R4. GUI depth: submission order is the rule, so no per-call z-translates are needed
- **Decision:** do not reintroduce manual z offsets for slot markers (count text, remainder/catalyst icons, highlights). EMI already draws them after the item in every path it owns, which is sufficient.
- **Verified against the decompiled 26.1.2 `GuiRenderState`:** `addGuiElement`, `addItem`, `addText` and `addPicturesInPictureState` all funnel through the same `findAppropriateNode(ScreenArea)`. That either steps `up()` one layer (when the previous element's bounds encompass the new one — e.g. an 18x18 slot background followed by its 16x16 item) or calls `navigateToAboveHighestElementWithIntersectingBounds`, which walks the current stratum's node chain and places the element one layer above the deepest node whose element **or item or text or picture-in-picture** states intersect it. So items are ordered against other elements by the same rule as everything else, and **a later, overlapping submission always lands above an earlier one.** `GuiRenderer.ELEMENT_SORT_COMPARATOR` only reorders elements *within* a layer (by scissor, pipeline, texture) for batching, which is safe because a layer holds no overlapping elements. `GuiGraphicsExtractor.nextStratum()` starts a whole new stratum above everything, which is what `flushDeferredTooltips` uses.
- **Consequence:** EMI's markers reliably draw above items — `ItemEmiStack.render` and `TagEmiIngredient.render` draw the icon, then the amount, then the tag/remainder icons, and `SlotWidget.extractRenderState` runs `drawBackground`, `drawStack`, `drawOverlay` in that order. No spot in the rendering files needed reordering.
- **Double-check:** in game, that counts and the small corner markers are never hidden behind a 3D block item, and that EMI's deferred tooltips still draw above the BoM/recipe screens.

## D-R5. Small rendering fixes restored to upstream behaviour
- Text colours no longer force `| 0xFF000000` unconditionally in `EmiDrawContext` and `EmiTooltipComponent.TextRenderData`. 1.21's `(color & 0xFC000000) == 0` rule was used at first; see D-R6.1 for why only a zero alpha is promoted now.
- `EmiScreenshotRecorder` no longer forces alpha on readback. Vanilla's `Screenshot` does that because it captures the main framebuffer; EMI renders into its own `TextureTarget` cleared to `(0, 0, 0, 0)`, so recipe screenshots get their transparent background back.
- `AbstractInventoryScreenMixin` only calls `EffectsInInventory.extractText` when the effect strip is `wide`, as upstream only called `drawStatusEffectDescriptions` when wide. Besides the text, 26.1's `extractText` also registers its own `setTooltipForNextFrame` when the name does not fit, which fought with the tooltip EMI defers itself in the compressed layout.
- `EmiDrawContext.DEFERRED_TOOLTIPS` is cleared when a new frame's raw context is seen and the list is copied-then-cleared before running, so a path that defers without flushing can no longer run a stale runnable against a dead context on the next frame.
- The effect exclusion area now tests `screen instanceof AbstractContainerScreen<?> && screen.showsActiveEffects()`. 26.1 has no `EffectRenderingInventoryScreen`: `EffectsInInventory` is composed into `InventoryScreen` and `CreativeModeInventoryScreen`, which expose it via the overridable `Screen.showsActiveEffects()` (default `false`). That is wider than the port's `instanceof` pair because a modded screen with an effects panel overrides it, and it also folds in vanilla's own `canSeeEffects()` room check.
- Dead code removed: `EmiDrawContext.overlay`/`setOverlay` (set, never read; not present upstream), `EmiDrawContext.getColor()`, `ItemEmiStack.unbatchable`, and the `getWidth` default that the port had added to `EmiTooltipComponent` (upstream has none and every in-tree implementor overrides it).

## D-F2. Recipe / sync / gameplay regression pass (branch `fix/f2-recipes`)

### D-F2.1 `/give` fallback rebuilt by hand — 26.1 deleted `ItemInput#serialize`
- **Decision:** `EmiPort.serializeItemArgument(ItemStack, HolderLookup.Provider)` rebuilds `namespace:id[component=snbt,!removed]` from `ItemStack#typeHolder`/`getComponentsPatch`, `BuiltInRegistries.DATA_COMPONENT_TYPE`, `TypedDataComponent#encodeValue` and `ItemParser`'s syntax constants. `EmiScreenManager.give` uses it instead of `"give @s " + is.getItem()`.
- **Why:** `javap` of 26.1.2 `net.minecraft.commands.arguments.item.ItemInput` shows a record with only `createItemStack(int)` — the `serialize(HolderLookup.Provider)` upstream used is gone, and no method with descriptor `(HolderLookup$Provider)String` exists anywhere in the jar. `Item#toString()` drops both the namespace and every component.
- **Double-check:** in-game, cheat a written book / dyed leather / enchanted item with EMI installed **client-side only** (no EMI on the server) and confirm the command round-trips.

### D-F2.2 `EmiSuspiciousStewRecipe` / `EmiMapCloningRecipe` deleted rather than re-registered
- **Why:** 26.1.2 has neither `SuspiciousStewRecipe` nor `MapCloningRecipe` (full listing of `net/minecraft/world/item/crafting/`). `data/minecraft/recipe/suspicious_stew_from_*.json` are now plain `minecraft:crafting_shapeless` recipes (17 of them, one per flower) and `map_cloning.json` is a `minecraft:crafting_transmute`, so the existing `ShapelessRecipe` and `TransmuteRecipe` branches already display them from vanilla's own data.

### D-F2.3 Custom-recipe shapeless heuristic: unknown shapes are displayed shapeless
- **Why:** upstream's `recipe.fits(w, h)` does not exist on 26.1's `Recipe`, and `PlacementInfo` only exposes a flat ingredient list plus a slot map that cannot recover a width. So: recipes with more than 9 ingredients are skipped (replacing `fits(3, 3)`), `ShapedRecipe`s that reach the generic branch are skipped (they are the oversized ones the branch above rejected), and everything else is emitted as a shapeless recipe.
- **Double-check:** a modded crafting recipe that is shaped but does not extend `ShapedRecipe` will now be shown as shapeless. There is no information left in the API to do better.

### D-F2.4 `ItemTags.DYEABLE` stays `ItemTags.CAULDRON_CAN_REMOVE_DYE`
- **Why:** `ItemTags` in 26.1.2 has no `DYEABLE` field; `data/minecraft/tags/item/cauldron_can_remove_dye.json` contains exactly the old dyeable set (4 leather armor pieces, leather horse armor, wolf armor).

### D-F2.5 One reload per world join, on both loaders
- **Decision:** recipes call only `EmiReloadManager.reloadRecipes()`, tags call only `reloadTags()`. Fabric tags come from `CommonLifecycleEvents.TAGS_LOADED` filtered to `client == true`; NeoForge tags come from `TagsUpdatedEvent.ClientPacketReceived`.
- **Why:** both loaders were calling both halves from a single event, so the two-phase mask in `EmiReloadManager` could never gate anything. Verified in the 26.1.2 jars: `TagsUpdatedEvent$ClientPacketReceived` is posted from `ClientConfigurationPacketListenerImpl` (join) and `ClientPacketListener` (`/reload`), while `ServerDataLoad` comes from `ReloadableServerResources`; Fabric fires `TAGS_LOADED` from the same two client listeners plus `ReloadableServerResources` with `client == false`.
- **Double-check:** the `client.level != null` guard had to be removed from the NeoForge tag listener, because tags arrive during the configuration phase before a level exists. The reload worker still refuses to run without a level.

### D-F2.6 NeoForge only requests the recipe payload when someone can receive EMI packets
- **Why:** `OnDatapackSyncEvent#sendRecipes` records recipe types for every player the event syncs to, so it cannot be filtered per player; `getRelevantPlayers().anyMatch(p -> p.connection.hasChannel(EmiNetwork.PING))` is the finest granularity the API allows.

### D-F2.7 NeoForge chess payload registered bidirectionally under `emi:chess`
- **Why:** `EmiPacketHandler` registered `emi:chess_s2c`/`emi:chess_c2s` while `EmiChessPacket#type()` returns `emi:chess`, so the channel was never registered and `hasChannel` always failed. `registrar(...)` takes a protocol version, not a namespace, so it is now `"1"`.

## D-R6. Second rendering pass (branch `fix/f1b-rendering`)

### D-R6.1 Recipe screenshots run vanilla's own `GuiRenderer` over vanilla's own `GuiRenderState`
- **Decision:** `EmiScreenshotRecorder.saveScreenshot` now takes a `Consumer<GuiGraphicsExtractor>`. It extracts the recipe into `GameRenderer.getGameRenderState().guiRenderState`, points `Minecraft.mainRenderTarget` and `WindowRenderState.{width,height,guiScale}` at its own `TextureTarget` for the duration of one `GuiRenderer.render(...)` + `endFrame()`, restores all of it in a `finally`, then reads the target back and destroys it. Two new accessor mixins carry this: `accessor/GameRendererAccessor` (`guiRenderer`, `fogRenderer`) and `accessor/MinecraftAccessor` (a `@Mutable` setter for `mainRenderTarget`).
- **Why the previous code produced blank PNGs:** the port built a detached `GuiRenderState` and only ever *extracted* into it. Nothing turns a `GuiRenderState` into pixels except `GuiRenderer`, so the `TextureTarget` only ever received its clear colour - fully transparent since the alpha-readback fix, i.e. an empty image.
- **Why vanilla's `GuiRenderer` instead of a fresh one:** `GuiRenderer`'s `renderState` is `private final`, so a private state needs a private renderer, and constructing one allocates its own `ByteBufferBuilder`, per-format ring buffers, `CubeMap` and item atlas, and would need the picture-in-picture renderer list (entities, banners, signs, books) that only `GameRenderer` builds. Reusing the shared instance costs nothing and keeps recipes with entity/banner renders working. Its state is safe to borrow: `GuiRenderer.render` ends with `renderState.reset()`, so it sits empty between frames, and this runs from `Minecraft.execute`/input handling, which `Minecraft.runTick` drains *before* `GameRenderer.render`.
- **Why the main-target swap is unavoidable:** verified in the 26.1.2 bytecode that `GuiRenderer.draw` reads `Minecraft.getMainRenderTarget()` directly for its colour/depth attachments, takes its ortho from `WindowRenderState.{width,height,guiScale}`, and that `enableScissor` and `getGuiScaleInvalidatingItemAtlasIfChanged` read the same window state. `RenderSystem.outputColorTextureOverride` is **not** consulted by `GuiRenderer` - only `GuiItemAtlas`, `PictureInPictureRenderer`, `LevelRenderer` and `RenderType` read it - so the override mechanism cannot redirect GUI draws.
- **Details:** the target is cleared to `0x00000000` with depth `1.0` before the render (`GuiRenderer` never clears) and keeps its depth view attached, matching `executeDrawRange`'s `useDepth ? getDepthTextureView() : null`. The projection buffer/type are saved and restored. The readback hoists `GpuTexture.getFormat().pixelSize()` into a local because `copyTextureToBuffer` defers its callback through `RenderSystem.queueFencedTask`, by which time the target has been destroyed; the copy itself is issued synchronously, so destroying the target immediately afterwards is safe. Failure to allocate or render logs and aborts instead of writing an empty PNG.
- **Also:** `EmiDrawContext.opaqueColor` now promotes only a *zero* alpha (`ARGB.alpha(color) == 0`) to opaque. 26.1's `GuiGraphicsExtractor.text` skips text exactly when `ARGB.alpha(color) == 0` and otherwise honours the alpha it is given; 1.21's "top six bits clear means opaque" convention no longer exists anywhere in the client, and applying it was silently making colours like `0x01FFFFFF` opaque.
- **Cannot be verified without running the game:** that the produced PNG is right side up and correctly scaled, that borrowing the shared `GuiRenderState` never collides with a frame in flight, and that no mod hooks `Minecraft.getMainRenderTarget` in a way the temporary swap upsets. The feature is off by default (`ui.recipe-screenshot-button`).

### D-R6.2 Tag models that only inherit an item or block model render that item
- **Decision:** while walking the parent chain, if nothing has declared any texture yet and the parent is `<ns>:block/<name>` or `<ns>:item/<name>` with an item `<ns>:<name>` in `BuiltInRegistries.ITEM`, record that item (`EmiTags.getTagIconItem(Identifier)`) instead of flattening the model to a texture. `TagEmiIngredient` renders `EmiStack.of(item)` with the same flags as the first-stack fallback (`-1 ^ RENDER_AMOUNT`), cached per ingredient, before trying texture layers.
- **Why:** `assets/minecraft/models/tag/item/logs.json` is just `{"parent": "minecraft:block/oak_log"}`, which D-R1 resolved to the flat `side` texture; 1.21 baked and drew the actual block. This covers the block tags (`#minecraft:logs`, `#minecraft:slabs`, `#minecraft:stairs`, `#c:stone`) and the plain item ones (`#minecraft:axes` -> `minecraft:item/diamond_axe`, `#c:armors/*`, `#c:seeds`, `#fabric:shears`, and the `c`/`fabric` models that chain through `minecraft:tag/item/*`). Template parents (`item/generated`, `block/cube_all`) have no item of that name, so they fall through unchanged, as do models that declare their own textures - the `emi:item/{half,third,quarter}_item` strips are untouched.

### D-R6.3 Tag-icon textures are validated and de-animated at reload
- **Decision:** `resolveTagIcon`/`splitTagIcon` now resolve each texture through the `ResourceManager` (`<ns>:textures/<path>.png`) and return null - falling back to the item or first stack - when it is missing. The PNG's IHDR is parsed for its real dimensions and `AnimationMetadataSection.calculateFrameSize` gives frame 0's height, both stored on `TagIconLayer` so the blit uses the texture's true size instead of assuming 16x16 and draws only the first animation frame. Layer lists are returned via `List.copyOf`.

### D-R6.4 `EmiTags`' icon maps are published as immutable snapshots
- **Decision:** `MODELED_TAGS`, `TAG_ICONS` and the new `TAG_ICON_ITEMS` are `private static volatile` and assigned once per reload with `Map.copyOf` from locals built by `registerTagModels`. Reads go through `EmiTags.getModeledTags()` / `getTagIcon()` / `getTagIconItem()`; `EmiTagKey.getCustomModel` uses the getter.
- **Why:** they were `HashMap`s cleared and refilled on the reload worker while the render thread read them through `EmiTagKey.getCustomModel()` and `TagEmiIngredient.render`, which can see a half-filled map or a resizing table.

### D-R6.5 A disabled `StackBatcher` allocates nothing
- **Decision:** `StackBatcher`'s constructor returns immediately when `isEnabled()` is false, leaving `imm`/`unlitFacade` null; `render(Batchable, ...)` gained the same guard the `EmiIngredient` overload already had. `EmiAgnos.canBatch`/`canBatchAgnos` are deleted from `EmiAgnos`, `EmiAgnosFabric` and `EmiAgnosNeoForge` (nothing referenced them; `forge/` is not built).
- **Why:** the batcher is permanently off on 26.1 (D7), yet every sidebar `ScreenSpace` still constructed one, and the constructor eagerly `malloc`ed a `ByteBufferBuilder` per render layer - megabytes of off-heap memory that was never used and never freed.

### D-R6.6 Smaller fixes
- `EmiDrawContext.lastContext` stores `System.identityHashCode` rather than the `GuiGraphicsExtractor` itself, so the previous frame's context is not pinned for a frame.
- `EmiDrawContext.flushDeferredTooltips` drains in a loop, so a tooltip runnable that defers another tooltip is not stranded until the next frame.
- `AbstractInventoryScreenMixin` passes `extractText` the width `extractBackground` returned, as vanilla's `EffectsInInventory.extractEffects` does, instead of the maximum width it offered.

## D-F2b. Recipe review follow-ups (branch `fix/f2b-recipes`)

### D-F2b.1 Fabric: the vanilla recipe packet is the single "recipes half" trigger, and a server that does not synchronize gets an empty map
- **Decision:** on Fabric, `ClientRecipeSynchronizedEvent` now only records the map; `ClientPlayNetworkHandlerMixin`'s `handleUpdateRecipes` hook is the one place that reports the recipes half, via `EmiClientFabric.onVanillaRecipesReceived()`. If no map was recorded for this connection by then, EMI logs one warning and installs `RecipeMap.EMPTY` before reloading. The two tag mixins are gone (`ClientConfigurationNetworkHandlerMixin` deleted, the `handleUpdateTags` injection removed); `CommonLifecycleEvents.TAGS_LOADED` with `client == true` is now the only tag trigger. The map is still cleared on `ClientPlayConnectionEvents.DISCONNECT`.
- **Why the vanilla packet and not the Fabric event:** `RecipeSyncImpl.sendRecipes` returns without sending anything when `ServerPlayNetworking.canSend(player, ClientboundRecipeSyncPayload.TYPE)` is false (vanilla server, or a server without Fabric's recipe API) and again when the per-connection serializer set produced no entries. The client only offers that set at all if `RecipeSyncImpl.getSyncedSerializers()` is non-empty (`ClientConfigurationPacketListenerImplMixin.sendSupportedRecipeSerializers`). So on a non-syncing server `ClientRecipeSynchronizedEvent` simply never fires and EMI would wait forever; the reload worker aborted with "Recipe Manager is null" and EMI showed nothing.
- **Ordering evidence (why no bounded-tick deferral is needed):**
  - `RecipeSyncImpl.onInitialize` registers `sendRecipes` on `ServerLifecycleEvents.SYNC_DATA_PACK_CONTENTS` under the `fabric:recipe_sync` phase, ordered after `Event.DEFAULT_PHASE`.
  - `fabric-lifecycle-events-v1`'s `PlayerListMixin` fires that event from exactly two places (`javap -v` of the mixin): `@Inject(method = "placeNewPlayer", at = @At(value = "NEW", target = "net/minecraft/network/protocol/game/ClientboundUpdateRecipesPacket"))` and `@Inject(method = "reloadResources", at = @At(value = "INVOKE", target = "Lnet/minecraft/network/protocol/common/ClientboundUpdateTagsPacket;<init>(Ljava/util/Map;)V"))`. Both are un-shifted, so the callback runs *before* the instruction it targets.
  - `javap -c` of 26.1.2 `net.minecraft.server.players.PlayerList` confirms the two sites are the only ones that touch `ClientboundUpdateRecipesPacket` anywhere in the server jar: `placeNewPlayer` constructs it at bytecode 400 (after the login packet at 261), and `reloadResources` constructs `ClientboundUpdateTagsPacket` at 49 and `ClientboundUpdateRecipesPacket` at 74.
  - So on both paths `ClientboundRecipeSyncPayload` is written to the connection strictly before the vanilla recipe packet.
  - That order survives to the client handler. `ClientPacketListener.handleUpdateRecipes` and `ClientCommonPacketListenerImpl.handleCustomPayload` both start with `PacketUtils.ensureRunningOnSameThread(packet, this, this.minecraft.packetProcessor())`, and Fabric's `ClientCommonPacketListenerImplMixin` injects at `HEAD` of `handleCustomPayload`, calls `addon.handle(payload)`, and on `RunningOnDifferentThreadException` (thrown by `AbstractChanneledNetworkAddon.handle` when `isOnReceiveThread()` is false) re-queues the same packet with `packetProcessor.scheduleIfPossible(...)`. Both packets therefore enter one FIFO `PacketProcessor` queue in arrival order and are drained in that order, and `ClientPlayNetworkAddon.receive` invokes the payload handler inline with no further scheduling.
- **Consequence:** with a syncing server there is exactly one reload per join and per `/reload`, using the synced map; with a non-syncing server there is exactly one reload using `RecipeMap.EMPTY`, so the item index, tags, world interactions, fuels and brewing still work and only crafting recipes are missing. The duplicate "Tags synchronized" log line is gone.
- **Double-check in game:** join a vanilla or plain-Fabric server and confirm the single warning plus a working index; join a server with EMI and confirm one reload with recipes; run `/reload` on both and confirm one further reload each.

### D-F2b.2 `ProxyRecipeManager.getRaw()` is unconditional again
- **Decision:** `getRaw()` returns `EmiAgnos.getRecipeMap()` with no level check. The `Minecraft.getInstance().level == null` guard moved into `streamMatches`, which is the only place the level is handed to `RecipeMap#getRecipesFor`; `getMatches`/`getFirst` inherit it.
- **Why:** `getRaw()` backs the public `EmiRegistry#getRecipeMap()`, which the vanilla plugin alone calls once per recipe type during a reload. A guard there let the map flip to null part-way through a reload and produce a half-populated recipe set. `isAvailable()` still means "a map has been received".

### D-F2b.3 Stonecutter button index is recomputed the way the server computes it
- **Decision:** `StonecuttingRecipeHandler` no longer reads `StonecutterMenu#getVisibleRecipes()` and no longer falls back to the synced recipe map's ordering. It computes `level.recipeAccess().stonecutterRecipes().selectByInput(wantedInput).entries()` itself and matches each entry's `recipe().optionDisplay().resolveForFirstStack(SlotDisplayContext.fromLevel(level))` against the recipe's output with `ItemStack.isSameItemSameComponents`, clicking only on a unique match.
- **Why:** `javap -c` of 26.1.2 `StonecutterMenu` shows `setupRecipeList` assigning `recipesForInput = level.recipeAccess().stonecutterRecipes().selectByInput(stack)` and `isValidRecipeIndex` bounding `clickMenuButton` against it, so that list *is* the server's index space. The menu only rebuilds it from `slotsChanged`, which has not run for the stack EMI just asked the server to place, so `getVisibleRecipes()` still describes the previous input. The old synced-map fallback matched only by coincidence of ordering and ignored the feature-flag filtering the server applies in `getSynchronizedStonecutterRecipes()`.
- **Note:** the client's `ClientRecipeContainer.stonecutterRecipes()` is the already-filtered set from `ClientboundUpdateRecipesPacket`, so client and server agree on both content and order.

## D-R7. Third rendering pass (branch `fix/f4a-rendering`)

### D-R7.1 Recipe screenshots render under the UI lightmap
- **Decision:** `EmiScreenshotRecorder` calls `gameRenderer.getLighting().setupFor(Lighting.Entry.ITEMS_3D)` and raises `GameRenderer.useUiLightmap` (new `@Accessor` setter on `GameRendererAccessor`; the field is not final, so no `@Mutable`) immediately before `guiRenderer.render(...)`, and lowers the flag again in the `finally`.
- **Why:** `javap -c` of 26.1.2 `GameRenderer.render` does exactly this around its own GUI pass (`getLighting():Lcom/mojang/blaze3d/platform/Lighting;` -> `Lighting$Entry.ITEMS_3D` -> `setupFor`, then `putfield useUiLightmap` with `iconst_1`, the `guiRenderer.render` / `endFrame` pair, then `putfield useUiLightmap` with `iconst_0`), and `GameRenderer.lightmap()` returns the world `Lightmap` whenever the flag is down. A screenshot taken from `RecipeScreenshotButtonWidget.mouseClicked` runs outside that pass, so items were being lit by wherever the player was standing - dark in a cave, tinted at sunset.
- **Also:** the screenshot scale is `Mth.clamp(scale, 1, 8)` rather than only floored at 1, and `WindowRenderState.guiScale` is only written when the screenshot actually wants a different one, since changing it invalidates the GUI item atlas (twice per screenshot, before and after).

### D-R7.2 `EmiTags` publishes one immutable snapshot, not three fields
- **Decision:** the three `volatile` maps of D-R6.4 are replaced by a single `private static volatile Snapshot`, an immutable `record Snapshot(modeled, icons, items)` built with `Map.copyOf` and assigned once per reload. `getModeledTags()` / `getTagIcon()` / `getTagIconItem()` keep their signatures and read the one field.
- **Why:** three separate volatile writes let the render thread pair one reload's `MODELED_TAGS` with the previous reload's `TAG_ICONS`, so a tag could resolve to a model id whose icon was not yet published and silently fall back to its first stack for a frame.
- **Also:** `TagIconLayer` gained `frameWidth`, taken from the `FrameSize` that `AnimationMetadataSection.calculateFrameSize` returns, and `TagEmiIngredient.render` slices `u`/`regionWidth` out of that instead of the full texture width, which was wrong for animations laid out in strips across. A malformed `.mcmeta` or an out-of-range frame size now degrades to the full texture size instead of dropping the icon, `readPngSize` checks that the first chunk really is `IHDR`, and `getTagIcon` is only consulted once `getTagIconItem` has missed.
- **Also:** `EmiDrawContext.flushDeferredTooltips` bounds its drain at 8 passes, so a tooltip runnable that always re-defers is left for the next frame rather than hanging the render thread.

## D-F4b. Recipe review follow-ups (branch `fix/f4b-recipes`)

### D-F4b.1 NeoForge: the vanilla recipe packet arms a bounded fallback, so a non-NeoForge server still reloads
- **Decision:** a new client mixin in the NeoForge source set, `dev.emi.emi.mixin.neoforge.ClientPacketListenerMixin` (listed in `neoforge/src/main/resources/emi-neoforge.mixins.json`), injects at `RETURN` of `ClientPacketListener#handleUpdateRecipes` and calls `EmiClientNeoForge.onVanillaRecipesReceived()`, which arms a one-shot 20-tick countdown. `EmiClientNeoForge.clientTick` (a `ClientTickEvent.Post` listener) counts it down; on expiry it warns once, installs `RecipeMap.EMPTY` when `EmiAgnosNeoForge.hasReceivedRecipeMap()` is still false, and calls `EmiReloadManager.reloadRecipes()` either way. `recipesReceived` stays authoritative - it records the map and reloads - and cancels the countdown first. `playerLoggedOut` clears the map, the countdown and both warn-once flags. The existing empty-recipe-types warning is unchanged.
- **Why:** `javap -c` of NeoForge 26.1.2.109 `net.neoforged.neoforge.common.CommonHooks.sendRecipes` shows the whole body guarded by `player.connection.getConnectionType().isNeoForge()`: `ifeq` jumps straight to `return` when it is false, so no `RecipeContentPayload` is ever sent. `ClientPayloadHandler.handle(RecipeContentPayload, ...)` is the only thing that posts `RecipesReceivedEvent`, so on a vanilla, Paper or Fabric server the event never fires, the reload manager's mask latched at 1 ("tags only") and EMI never reloaded at all.
- **Ordering evidence (why this arms a countdown instead of reporting the half directly, unlike Fabric's D-F2b.1):** `javap -c` of the NeoForge-patched 26.1.2 `net.minecraft.server.players.PlayerList` shows `CommonHooks.sendRecipes` called *after* the vanilla packet on both paths:
  - `placeNewPlayer`: bytecode 428 constructs `ClientboundUpdateRecipesPacket`, 445 `ServerGamePacketListenerImpl.send(Packet)`, then 459 `CommonHooks.sendRecipes(ServerPlayer, Set, RecipeMap)`.
  - `reloadResources`: bytecode 95 constructs the packet once, and inside the per-player loop 150 `send(Packet)` then 173 `CommonHooks.sendRecipes(...)` for that same player.

  So on a NeoForge server the payload arrives strictly *after* the vanilla packet, and the vanilla packet cannot be the trigger the way it is on Fabric - it would report the half with the previous map still installed. 20 ticks is a very generous bound on two packets written back to back on one connection, and it is a bound rather than an unlimited wait only so a non-synchronizing server cannot hang the reload.
- **Why it re-arms on every packet:** a `/reload` on a vanilla server re-sends both vanilla packets, and `hasReceivedRecipeMap()` is already true then (the empty map from the join), so the countdown must still fire `reloadRecipes()` - it just leaves the recorded map alone and skips the warning. That is why the "has a map" check gates only the warning and the `RecipeMap.EMPTY` write, not the reload.
- **Threading:** the vanilla packet handler, NeoForge's payload handler and `ClientTickEvent.Post` all run on the client thread, so `recipeFallbackTicks` needs no synchronization. `receivedRecipeMap` stays `volatile` as before, because the reload and render threads read it.
- **Double-check in game:** join a vanilla/Paper server with the NeoForge client and confirm one warning plus a working item index; join a NeoForge server and confirm a single reload *with* recipes and no warning; run `/reload` on both and confirm exactly one further reload each.

### D-F4b.2 Fabric: the synchronized map is consumed per vanilla packet
- **Decision:** `ClientRecipeSynchronizedEvent` stores a *pending* map (`EmiAgnosFabric.setPendingRecipeMap`); `EmiClientFabric.onVanillaRecipesReceived` takes it with `consumePendingRecipeMap()` and installs it. When nothing is pending it warns once per connection - a `warnedAboutMissingRecipes` flag reset on `DISCONNECT`, alongside clearing both maps - and installs `RecipeMap.EMPTY`.
- **Why:** reading `hasReceivedRecipeMap()` could not tell "this sync produced a map" from "a previous sync did". A `/reload` whose sync sends no payload (a datapack that removes Fabric's synchronized serializers, or a server that stops synchronizing) therefore silently kept the stale pre-reload map and logged nothing. Consuming it makes the fallback per sync, and moves the warning from once per connection-that-never-synced to once per connection that fails to sync.

### D-F4b.3 The stonecutter index is computed from the stack actually placed
- **Decision:** `StonecuttingRecipeHandler.craft` now calls `EmiRecipeFiller.getStacks(this, recipe, context.getScreen(), context.getAmount())` before delegating to `StandardRecipeHandler.super.craft`, bails out without clicking anything when that is null/empty, and passes `stacks.get(0)` to `findRecipeIndex` as the input. `findRecipeIndex` takes the stack as a parameter instead of reading `recipe.getInputs().get(0).getEmiStacks().get(0)`. The method returns `action && index >= 0`, and logs once when the index could not be resolved.
- **Why:** the server's index space is `stonecutterRecipes().selectByInput(input)` for the item that is really in the slot (D-F2b.3). For a tag input, `EmiRecipeFiller` places whichever matching item the player happens to have, which is generally not the ingredient's first stack, so the list being indexed was the wrong one and the click selected an unrelated recipe or none. Reporting `true` while nothing was selected also told EMI the craft had succeeded when only the input had been moved.

### D-F4b.4 JEMI fixes
- **Scroll grid clipping:** `JemiScrollGridWidget.isClipped(IRecipeSlotDrawable)` reports slots the grid owns but never laid out, and `JemiRecipe.addWidgets` skips building a slot widget for them - they were all stacking up at (0, 0) over the recipe. The cell backgrounds now cover the full `gridWidth * gridHeight` rectangle, which is what JEI's own `ScrollGridRecipeWidget` draws. The dead `getOccupiedRows()` is deleted.
- **Recipe-type gate:** `type.getRecipeClass().isInstance(rawRecipe)` is a no-op for a vanilla type, because `IRecipeHolderType.JeiRecipeHolderType.getRecipeClass()` returns `RecipeHolder.class` for every one of them (`javap -c` of JEI 29.40.0.101). `isOfHolderType` additionally compares `BuiltInRegistries.RECIPE_TYPE.getKey(holder.value().getType())` with `type.getUid()`, which `JeiRecipeHolderType` derives from exactly that registry key, and skips `setRecipe` on a mismatch.
- **Slots-view memo:** the per-instance memo never hit, because `JemiPlugin.getRecipeHandler` constructs a new `JemiRecipeHandler` on every call - i.e. every frame - so the whole JEI layout was rebuilt per frame. It is now two static `WeakHashMap<EmiRecipe, CachedView>`s (positioned / bare) that also record the `IRecipeType` the view was built for, cleared from `JemiPlugin.register` where `CATEGORY_MAP` is cleared. A weak `FAILED_VIEWS` set makes a recipe whose view throws log once instead of once per frame.
- **Matrix restore:** the `finally { draw.pop(); }` after a third-party `IRecipeTransferError.showError` is wrapped in its own try/catch, so an implementation that pops the matrix stack more often than it pushes cannot throw out of `render()`.
- **`createDisplayOverrides` is idempotent:** it lazily creates one acceptor and returns the same one on every call, as JEI's own slot does; `clearDisplayOverrides` resets it. A plugin calling it per ingredient used to get a separate override each time, which EMI then merged into a list ingredient instead of one override.
- **`JemiTooltipBuilder`:** `lines` is the single source of truth, `getLines()` returns the live mutable list (JEI's `JeiTooltip.getLines()` does the same, so plugins expect their edits to stick), and the `ClientTooltipComponent`s are derived on read by `buildTooltip()`. The four consumers - `JemiSlotWidget`, `JemiRecipe`, `JemiStack`, `JemiPlaceable` - call it.

### D-F4b.5 The fill packet's expanded slot list is bounded on its own
- **Decision:** `FillRecipeC2SPacket.parseCompressedSlots` keeps `MAX_SLOTS = 65536` as the bound on individual indices and adds `MAX_EXPANDED_SLOTS = 4096` as the bound on how many entries all ranges expand to together.
- **Why:** the old check bounded the expansion by `MAX_SLOTS` too, so a six-byte packet declaring one range of `0..65535` still cost the server 65536 boxed integers. No real menu has that many input sources, and large indices stay legal for modded menus. The inaccurate "the buffer is shared with the rest of the connection" comment is replaced: `PacketDecoder` decodes one framed packet, which is exactly why throwing `DecoderException` is the right response - it rejects this packet cleanly.

### D-F4b.6 The "no recipes synchronized" warning triggers on an empty map
- **Decision:** `VanillaPlugin.register` warns when `registry.getRecipeMap()` is null *or* `map.values().isEmpty()`.
- **Why:** both loaders now always install a map, falling back to `RecipeMap.EMPTY` on a server that does not synchronize, so the null case alone no longer describes "no recipes arrived".

## D-F4c. Round-4 corrections (applied directly on `26.1`)
- **NeoForge vanilla-packet fallback reverted (D-F4b.1 superseded).** The round-4 reviewer showed from the 26.1.2.109 bytecode that NeoForge's patched `ClientPacketListener.handleUpdateRecipes` calls `ClientHooks.handleUpdateRecipes`, which posts `RecipesReceivedEvent` inline with an empty map on every non-NeoForge connection (`CommonHooks.sendRecipes` only sends the payload to NeoForge connections). So `RecipesReceivedEvent` already fires exactly once per vanilla recipe packet on every server kind, and the countdown/mixin added in D-F4b.1 double-reported the recipes half and latched the reload mask at "recipes only" (subsequent `/reload`s would then reload on the tags packet with stale data). `ClientPacketListenerMixin`, the tick countdown and the second warning are gone; `emi-neoforge.mixins.json` is empty again; the existing "server did not synchronize any recipes" warning is the vanilla-server signal.
- **Stonecutter:** the button index is resolved before the fill packet is sent, so an unresolvable recipe is refused with no side effects instead of moving the item and then reporting failure.
- **Tag icons:** `EmiTags.snapshot()` + `EmiTagKey.getCustomModel(Snapshot)` let `TagEmiIngredient.render` do all three lookups against one snapshot; a malformed `.mcmeta` is logged once via `EmiReloadLog`.
- **JEMI:** an unregistered recipe type no longer blocks `setRecipe` (`isOfHolderType` allows a null registry key); `onRuntimeUnavailable` clears the slots-view caches; the scroll-grid list survives a throwing `createRecipeExtras`.
- **Screenshots:** `useUiLightmap` is restored to its previous value rather than `false`.
- **Left as noted (MINOR/INFO in round 4):** `consumePendingRecipeMap` is a two-step read on a volatile (client thread only); the stonecutter warn-once flag is process-wide; `FillRecipeC2SPacket` rejects indices above 65536 (comment corrected); `VanillaPlugin`'s empty-map warning also shows on a server that ships no recipes at all.
