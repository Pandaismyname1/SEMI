# Decision log: SEMI 26.3 port (autopilot, 2026-09-22)

## F1. Same recipe as 26.2: port on top of SEMI's `26.2`, using the community fork's 26.3 delta as the answer key
- **Decision:** branch `26.3` from SEMI's released `26.2` and re-implement, hunk by hunk, what `link-fgfgui/emi@26.3` changed between its 26.2 and 26.3 branches (63 files, +719/-520: tool-item and brewing accessors, input handling, the two C2S packets, JEMI for JEI 31, config screens, the screenshot recorder), instead of merging the fork's branch.
- **Why:** the fork's branches do not carry SEMI's review/fix rounds; a merge would reintroduce regressions. The delta is three times the size of the 26.2 one, so the port worker gets the fork's per-commit patches plus the first build's compile-error list as its work list.

## F2. Toolchain pinned to the newest 26.3 releases available on 2026-09-22
- Minecraft 26.3, Fabric Loader 0.19.5, Fabric API 0.161.0+26.3, ModMenu 21.0.0-beta.1 (the only ModMenu line for 26.3), NeoForge 26.3.0.8-beta (NeoForge has published only beta builds for 26.3 so far; the fork used 26.3.0.1-beta), JEI API 31.4.0.19 (the fork used 31.0.0.5). Gradle 9.5.0 + loom-no-remap 1.17.493 kept.
- **Double-check:** when a non-beta NeoForge 26.3 build appears, bump `neoforge_version` and re-run the NeoForge client; the `[26.3,27)` dependency range already accepts it.

## F3. `EmiRegistry#getRecipeMap` and `RecipeMap` are kept; only Fabric's construction changed
- **Decision:** SEMI keeps `net.minecraft.world.item.crafting.RecipeMap` everywhere, including the public `EmiRegistry#getRecipeMap()`, instead of following the community fork's switch to a plain `Collection<RecipeHolder<?>>`.
- **Why:** `RecipeMap` still exists in 26.3, and NeoForge still hands EMI one from `RecipesReceivedEvent`. Only `RecipeMap.create` changed: it takes a `HolderLookup<Recipe<?>>` now that recipes are a datapack registry, which the plain collection Fabric's `ClientRecipeSynchronizedEvent` hands out no longer satisfies (NeoForge patches in its own `RecipeMap.createClient` for exactly this; Fabric has no equivalent). Dropping `RecipeMap` would have broken a published API method every third-party EMI plugin can call, and would have replaced `RecipeMap.byType`/`byKey` — which SEMI's `ProxyRecipeManager` uses on hot paths such as crafting-result detection and stonecutting — with linear scans over every recipe.
- **How:** `EmiClientFabric.toRecipeMap` registers the synchronized recipes into a throwaway `MappedRegistry<Recipe<?>>` (public API: `MappedRegistry`, `register`, `RegistrationInfo.BUILT_IN`, `freeze`) and feeds that to `RecipeMap.create`. A recipe that cannot be registered (duplicate id) is skipped with a log line rather than losing the whole map.
- **Double-check:** the fork's `getRecipes()` shape is the only visible difference between SEMI's and the fork's 26.3 API.

## F4. Composting chances and fuel burn times are resolved from the integrated server only
- **Decision:** `EmiPort.getExpectedValue(ResolvableInt)` resolves a `ResolvableInt.Reference` through `Minecraft.getSingleplayerServer().reloadableRegistries()` first, and through the client's registry access second. When neither has the registry the value is 0, the item is left out of the fuel/composting lists, and one reload warning per category says so.
- **Why:** 26.3 moved composting to the `compostable` component and fuels to the `cooking_fuel` component (`Level#fuelValues` and `ComposterBlock.COMPOSTABLES` are both gone). Both components hold a `ResolvableInt` that normally points into the `minecraft:context_int_provider` registry, and that registry is in `RegistryDataLoader.RELOADABLE_REGISTRIES`, not in `SYNCHRONIZED_REGISTRIES` — the server never sends it, on either loader. The community fork reads it from `client.level.registryAccess()`, which is always empty, so its composting and fuel categories are empty everywhere. Going through the integrated server keeps both categories correct in singleplayer and on a LAN host, which is where they can be correct at all.
- **Known gap:** on a remote server the Fuel category and the composting recipes are empty (with a warning in the reload log). Closing that needs EMI's own server-side component to send the resolved values, which is a protocol change, not a port fix.
- **Double-check:** `getExpectedValue` follows a dispatcher's default branch and a conditional's false branch, so it reports what a player sees in normal use: coal resolves to `1600 / 1` ticks, `compostable/low` to `0.3`, `compostable/always_add_one` to `1.0` — the same numbers 26.2 showed.

## F5. Tool interaction recipes lose the extra drop, and tooltips keep 26.2's spacing
- Stripping, tilling and flattening now come from the `minecraft:block_transformer` registry (which *is* synchronized), read through three new block-predicate accessors. A transform may also roll a loot table (tilling rooted dirt drops hanging roots); loot tables are server side, so that second output is no longer part of the displayed recipe. The block-to-block result is unchanged, and the axe transformer also covers the copper de-waxing and de-oxidising that used to come from `WeatheringCopper`/`HoneycombItem`.
- `GuiGraphicsExtractor.tooltip` gained a trailing boolean that controls the gap after the first tooltip line. SEMI passes `true` at all five call sites, which is byte-for-byte 26.2's layout; the community fork passes `false`, which makes every multi-line tooltip background two pixels short.

## F6. Mouse buttons renumbered
- 26.3 renumbered the mouse buttons (left 0→1, middle 2→2, right 1→3) along with the switch to SDL scancodes, so every literal comparison in EMI is now an `InputConstants.MOUSE_BUTTON_*` constant and `EmiScreenManager.isClickClicky` accepts 1..3. Binds are stored by key *name* (`key.mouse.left`, `key.keyboard.o`), so existing config files keep working.

## F7. `EmiPort` is client-free by rule (in-game finding 1)
- **Decision:** `dev.emi.emi.EmiPort` must contain no reference to a `net.minecraft.client.**` type at all — not in a field type, a method signature, a local variable or a cast. Anything that needs one lives in `EmiPortClient`.
- **Why:** `EmiNetwork`'s static initializer calls `EmiPort.id(...)`, so a dedicated server loads and verifies `EmiPort` during mod init. The 26.3 `getContextIntProviders` assigned `Minecraft.getSingleplayerServer()` (an `IntegratedServer`) to a `MinecraftServer` local, and the verifier must load `IntegratedServer` to prove that assignment; the class does not exist on a server, so both loaders died at their `main` entrypoint. Only a *subtype check* forces the load, so the previous releases got away with `Minecraft`, `Button` and `EditBox` in `EmiPort`'s signatures — the rule above is the version that cannot be got wrong by accident.
- **Check:** `javap -p -v` on the built and the packaged `EmiPort.class` reports zero `net/minecraft/client/` constant pool entries. The same scan over every class a server loads during init (`EmiMainFabric`, `EmiNeoForge`, `EmiPacketHandler`, `EmiMain`, `EmiNetwork`, the five packets, `EmiCommands`, `EmiLog`) is clean; `EmiAgnos` and its two loader subclasses still carry client types in method descriptors, exactly as in 26.1 and 26.2, whose server runs passed.

## F8. Transmute recipes are assembled against a real grid (in-game finding 2)
- 26.3's `TransmuteResult` has an optional item: `KEEP_INPUT_ITEM` takes the output item from the stack that matched the recipe's input ingredient, and `add_material_count_to_result` adds the number of matched material stacks to the count. Assembling from `CraftingInput.EMPTY` therefore resolves the item from air and throws. `EmiPortClient.getOutput` assembles a transmute recipe against a 2x1 grid of one input stack plus one material stack, read through a new `TransmuteRecipeAccessor` because both ingredients are private and `PlacementInfo` does not distinguish them.
- **Double-check in game:** map cloning should show two filled maps; the shulker box and bundle recolouring recipes previously fell through to the slot display and now assemble, so their outputs are worth a look too.

## F9. The server sends the resolved number provider values (review round 1, finding G; supersedes the F4 gap)
- **Decision:** a server running SEMI evaluates its whole `minecraft:context_int_provider` registry once and sends the results — `Map<Identifier, Float>` — to SEMI clients on EMI's own channel, as `emi:context_int_values`. A client resolves a `ResolvableInt.Reference` from the received values first, then from the integrated server's reloadable registries, then from the synced registry lookup (always empty), and warns once per category when none of them has anything.
- **Why the configuration phase:** the values must be on the client before it enters play, so that the one EMI reload per join already sees them. Fabric adds a `ConfigurationTask` from `ServerConfigurationConnectionEvents.CONFIGURE`, which Fabric injects at the head of `startConfiguration`, so it runs before vanilla's `SynchronizeRegistriesTask` and therefore before the tags; NeoForge's `RegisterConfigurationTasksEvent` is posted from `addOptionalTasks()`, after the registry and tag sync but still well before the play phase and the recipe packet. Either way the values are in place before EMI's tags/recipes handshake completes. Both tasks are registered only when the connection announces the channel (`ServerConfigurationNetworking.canSend` / `listener.hasChannel`), so a vanilla client is untouched.
- **Why no channel version bump:** the payload is a new id on the existing optional channel (`registrar("1").optional()` on NeoForge, a plain `PayloadTypeRegistry` registration on Fabric). An older SEMI simply never announces `emi:context_int_values` and is skipped; nothing about the existing packets changed, so bumping the version would only break the handshake with those older clients for no gain.
- **Datapack reloads, and why the reload trigger is its own thing:** the values are re-sent in the play phase (Fabric `ServerLifecycleEvents.END_DATA_PACK_RELOAD`, NeoForge `OnDatapackSyncEvent` with a null player, both guarded by the same channel checks). A receiver must never call `EmiReloadManager.reloadRecipes()` for this: that is one half of the two-half tags/recipes handshake, and ORing its bit into `loadedResourcesMask` out of band leaves the mask stuck and throws every later reload off by one half.
- **How a data change actually reloads:** `EmiReloadManager.reloadForDataChange()` never reloads and never touches the mask; it only records a debt (`pendingDataChange`) and starts a grace period of 40 client ticks. Every reload clears the debt, so a handshake that follows the values pays it — which is the normal case on NeoForge, where `OnDatapackSyncEvent` fires before the tags and recipes. `clientTick()` pays it only if the grace runs out with no handshake in sight, which is the Fabric case, where `END_DATA_PACK_RELOAD` runs after both have been broadcast. The grace timer is reset for as long as a handshake is in progress. Before reloading on its own it checks `Minecraft.getInstance().level != null`, because `status` is not per connection: a worker finishing its unchecked tail after a disconnect used to publish `status = 2` over the reset `clear()` had just done, and the configuration phase and reconfiguration both leave the level null with EMI still nominally loaded. The worker now publishes `status = 2` under the lock and only when neither a restart nor a clear was asked for.
- **Reload counts:** a fresh join is one reload on both loaders, and so is a `/reload` whose values did not change (nothing is scheduled, because `set` reports no change) and a `/reload` whose values did change on NeoForge (the values arrive first and the handshake's reload consumes the debt). A `/reload` with changed values on Fabric is two, because the values genuinely arrive after the reload that the tags and recipes triggered; there is no way to fold that into one without delaying every reload. A disconnect during a reload, and a reconfiguration, produce no stray reload at all.
- **Reconfiguration:** a configuration phase arrival is treated exactly like a play phase one, because the debt-and-grace rule needs no phase knowledge. On a join the grace expires against a null level and the debt is dropped, and the join's own handshake reload uses the values anyway; a reconfiguration ends in the tags and recipes being re-sent, so its handshake reload pays the debt too. Singleplayer is unchanged: the integrated server's values arrive before anything is loaded and match what the local lookup would have produced.
- **Common code:** the evaluation lives in `dev.emi.emi.data.ContextNumbers`, which the server uses to build the map and the client uses for whatever it can reach locally. It refuses to recurse more than 64 providers deep, because a datapack can make them reference each other in a loop and a `StackOverflowError` would otherwise escape past the join and the reload worker. `EmiPort` and every packet class stay free of `net.minecraft.client` references (verified with a constant pool scan).
- **What the server does not send:** a provider EMI cannot estimate is left out of the payload rather than sent as zero, so the client still falls back to its own lookup and still reports it. The values are computed once per datapack state — on server start and after every datapack reload — and cached, so the evaluation and everything it logs happen once rather than once per joining client. The client tracks "a values packet arrived" separately from "the map has entries", so a SEMI server whose providers were all unhandled is not blamed for not running SEMI.
- **Double-check:** on a server without SEMI the Fuel category and composting are still empty, now with a reload warning that says why (reviewer's finding B reworded both "no synchronized recipes" messages too: brewing is a recipe type in 26.3, so it needs recipe synchronization, and fuels and composting need the server).

## F10. Number provider coverage and per-reload resolution (review round 1, finding D)
- `ContextNumbers` handles every shared provider shape rather than the five vanilla happens to use: aggregates (sum, product, average, minimum, maximum, and the float `length`), unary operations (absolute, negate, ceiling, floor, round, truncate, square root, sine, cosine, and the int/float conversions), ranges (midpoint), binary operations (difference, quotient, modulus, floor quotient, floor modulus), powers, dispatchers (default branch), conditionals (false branch) and weighted lists (weighted mean), for both the int and the float provider families. Anything left — scoreboard, storage, environment attribute, binomial, enchantment level — produces one `EmiReloadLog` line naming the provider type per reload instead of a silent zero.
- The registry lookup is resolved once per reload into an `EmiPortClient.ContextIntSource` and passed down, instead of being rebuilt per item; the composting pass now precomputes the chances into a map so the comparator does no work at all.
